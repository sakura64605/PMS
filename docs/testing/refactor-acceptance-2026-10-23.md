## 先准备

使用现有前端站点，页面路由见各项。API 的统一前缀为 `/pet-system`，后端进程监听 8080，前端代理地址沿用当前部署。以下接口路径均写在该前缀之后；参数及示例以当前源码为准。

准备普通账号 A、B、C 和管理员账号。A/B 用于互动，C 验证“不是自己的数据”。用两个浏览器或普通/无痕窗口分别登录，避免切换账号时误用缓存 token。管理员可以继续使用现有账号，普通测试账号用你自己的测试账号即可。本清单不写入任何密码或 token。

建议创建标题前缀 `验收20261023-` 的领养帖、救助帖、活动和日常，用这些数据执行写操作；记录内容 ID、评论 ID、举报 ID 和会话 ID。举报用户禁用、禁言测试放最后做，避免影响前面的互动。

网页提示“成功”不等于验收通过：刷新、换账号后核对数据；必要时在浏览器开发者工具 Network 中核对业务 `code`、`data`、`records` 和 `total`。业务拒绝可能通过响应体 code 表达，不能只看 HTTP 状态码。并发/越权/大页码测试没有按钮时，用 Network 的 Copy as fetch 或 Postman 复用真实请求，仅修改所列 ID/参数，不分享登录 token。

## 6. Feed（新实现）

页面：`/feed`。活动沿用 status=1 的可见规则，报名中/已结束活动不因本轮改造自动纳入。

| 编号 | 操作 | 预期 | 接口提示 |
|---|---|---|---|
| D01 | A 关注的作者分别有宠物帖与活动，打开并翻页 | 两类按时间统一排序；total 合理，稳定数据下翻页不反复出现同一首页内容 | GET /feed/home?pageNum=…&pageSize=… |
| D02 | 如有拉模式作者，混合普通作者查看 | 最新内容不会因“先取普通作者一页”而被遗漏；宠物/活动同 ID 也不合并 | 同上；拉模式需实际配置/达到原粉丝阈值，无该数据可先跳过 |
| D03 | 查看未读数，仅打开一页后再查 | 只消耗本页实际展示的投影，其他页、其他用户未读不被清除 | GET /feed/unread-count |
| D04 | B 内容被拒审、删除/下架，A 再刷新 | Feed 不展示相应内容，未读数不继续被这类投影抬高 | GET /feed/home、/feed/unread-count |
| D05 | A 取消关注 B，再刷新 | B 不再出现在 A 的当前 Feed；不影响别人的 Feed | 同上 |
| D06 | 有历史 adopt/help 大小写类型及重复投影时查看 | 能读取为 pet，同一动态只展示/计未读一次 | 需要历史数据；不必手工向服务器塞脏数据 |
| D07 | 页码超出范围、pageSize 特别大 | 空页保留 total，单页最多 100；不报错 | 同上 |

注意：拉模式内容若没有收件箱投影，不凭空产生未读数；offset 跨请求时有新增内容仍可能移动，不能据此要求游标级稳定快照。

## 7. 私信（新实现）

页面：`/private-message`。用 A/B/C 三个独立登录窗口验证。

| 编号 | 操作 | 预期 | 接口提示 |
|---|---|---|---|
| M01 | A 发给 B；B 回复；两个窗口同时发 | 同一对用户只有一个会话，两条消息都保存；各自未读与实际收到消息一致 | POST /message/private/send，JSON {"toUserId":B,"messageType":1,"content":"验收私信"} |
| M02 | A/B 同时从对方主页开始聊天 | 获取到同一会话，不重复创建 | GET /message/private/conversation?otherUserId=… |
| M03 | B 打开会话、显式标已读，同时 A 再发一条 | 消息不丢失，未读与最终消息已读状态一致，刷新后不出现旧计数覆盖新消息 | GET /message/private/messages；PUT /message/private/read/{conversationId} |
| M04 | A 清空或删除自己的聊天记录，B 刷新 | A 看不到旧记录/旧预览；B 的记录和预览仍在；后续新消息仍可到达 | DELETE /message/private/messages/{id}、/conversation/{id} |
| M05 | C 复用 A/B 的 conversationId 获取记录、标已读、清空、删除 | 四种操作均被拒绝；即使 A/B 刚读取过也不能因缓存泄露 | 上述会话接口 |
| M06 | 连续发两三条，分页核对记录与 total | 升序稳定，同秒消息用 ID 排序；不存在跨会话记录 | GET /message/private/messages?pageNum=…&pageSize=…&conversationId=… |
| M07 | 发约 800 字正文，再发超过 1000 字/空白/类型 9/给自己 | 800 字保存完整、预览不超过 500 字；其余请求被拒绝 | POST /message/private/send |
| M08 | B 在线/离线各接收一条，再重新进入 | 在线实时出现，离线消息可从数据库历史读取；实时推送失败不应导致已保存消息消失 | 页面及 GET /message/private/conversations、/unread-count |

删除目前只清除本人可见消息，**会话容器会保留，列表可显示空预览**；尚无独立的“仅对某人隐藏整个会话”字段。这与永久移除列表不是同一件事。

## 8. 站内通知（新实现；原 MQ/WebSocket 传输复用）

页面：`/message`。通知由上面的点赞、评论、关注、审核、活动等业务触发，没有对普通用户开放任意发送通知接口。

| 编号 | 操作 | 预期 | 接口提示 |
|---|---|---|---|
| N01 | 触发点赞、评论、关注、审核通过/拒绝通知 | 接收者、文案、目标 ID、链接正确，不发送给错误账号；PUNISHMENT 分类仍兼容 | GET /message/list?type=… |
| N02 | 单条标已读，再次标同一条 | 未读减少一次；首次 readTime 不因重复点击变成新时间 | PUT /message/read/{id} |
| N03 | 按 FOLLOW/LIKE 等分类全部已读 | 只清当前账号该类型；其他类型/账号不变 | PUT /message/read-all?type=FOLLOW |
| N04 | 不指定类型全部已读 | 只清当前账号全部未读 | PUT /message/read-all |
| N05 | C 复用 A 的通知 ID 标已读 | 拒绝，不改变 A 的通知；列表和未读仅能看自己 | GET /message/unread-count；PUT /message/read/{id} |
| N06 | 让重复审批/无效评论等失败，不另起成功业务 | 失败事务不产生对应通知；成功操作才有通知 | 结合审核和评论操作 |
| N07 | 翻页，按消息类型筛选；同秒多条通知 | total 正确，ID 作为同时间排序依据；默认 20，最多 100 | GET /message/list |

不建议为了验收直接停线上 MQ；真实 MQ 故障恢复和消费幂等仍为后续专项。进程内提交后事件并非持久化可靠投递，不保证重启瞬间的通知绝不丢失。

当前非定时创建默认直接发布。**不要在定时测试中途反复修改、取消定时时间来期待旧任务自动失效**：原任务模型尚无版本号/取消协议，这属于已知待完善项。

## 10. 举报（新实现）

使用内容页的举报入口；后台管理入口以现有菜单为准。举报类型用 pet/activity/comment/user，不支持日常举报。

| 编号 | 操作 | 预期 | 接口提示 |
|---|---|---|---|
| R01 | A 举报 B 的测试帖子，随后重复提交 | 第一条待处理，处理前重复提交被拒绝，不新增多条 | POST /report/submit，JSON {"targetType":"pet","targetId":ID,"reason":"验收举报"} |
| R02 | 管理员按状态/类型筛选并打开详情 | 举报人、处理人、目标标题和 total 对应 | GET /report/list、/report/detail/{id} |
| R03 | 管理员受理已发布帖子举报 | 举报变已处理，帖子下架；Feed/详情/搜索相关缓存更新需刷新观察 | POST /report/handle/{id}?status=1&handleResult=验收处理 |
| R04 | 受理报名中或进行中的活动举报 | 活动设为下架状态 3，不写无效状态 4；已结束活动不强改 | 同上 |
| R05 | 驳回一条举报 | 状态变已驳回，不下架目标、不处罚用户 | status=2，handleResult 填原因 |
| R06 | 两个管理员窗口同时处理同一举报，或再次处理已完成举报 | 只有一次决定成功，不重复处罚；不能 status=0 回退为待处理 | 同上 |
| R07 | 受理专用测试评论举报 | 评论软删除；作者禁言标记与截止时间落库，不缩短已有更长禁言；恢复任务按现有机制执行 | targetType=comment |
| R08 | 受理专用测试用户举报 | 正常账号禁用并创建一天后的恢复任务；不要对验收 A/B 过早执行 | targetType=user |
| R09 | 举报不存在目标、空白/超过 200 字原因；非管理员处理 | 拒绝；处理结果也要求 1–200 字，处理状态仅 1/2 | 上述接口 |

禁言后所有旧业务入口是否实际阻止发言、禁用后已签发 JWT 是否立即失效、人工永久禁用与旧自动解禁任务的协调，并非本轮已解决项。账号处罚放到全部正常流程之后单独测试。

## 11. 不能当作“这轮已重构成功”的功能

- 评论删除：现 Controller 的服务调用仍被注释，只返回成功提示；不要把提示成功当真实删除。
- XXL-JOB：当前源码没有 XXL-JOB 依赖或执行器，定时任务仍由 DelayTaskScheduler 每 60 秒查 delay_task。此前提出的 XXL-JOB 迁移尚未完成。
- 后台用户列表/批量启停/重置密码仍走旧账号服务；只有旧宠物审批入口接入新审核命令。
- 活动报名/取消报名/签到、日常推荐、AI、搜索主查询、统计报表、账号/头像/分类管理没有整体重写。可做冒烟，不能算这些模块已完成重构。
- 搜索索引同步与通知提交后副作用可能受外部服务影响，当前没有完整持久化补偿/重放保证；异常时应记录内容 ID、操作时间和请求响应。
- 物理新表切换未做，继续复用原业务表；没有数据库迁移验收项。
- 后端这次部署不包含前端重建。如果页面字段、状态提示与后端实际响应不一致，记录 Network 响应，区分页面展示问题与后端数据问题。
