# HTTPS 间歇失败排查记录

## 现象与范围

2026-10-27，用户反馈 `https://www.petcircle.tech` 时好时坏。外部检查复现了TLS握手重置，以及握手后尚未收到HTTP响应即断开。问题发生在业务API之前，不应据此修改数据库查询、Redis缓存或地图Key。

本记录只讨论证据与已执行的操作。证书、TLS协议、系统代理及云安全组没有因为推测而被修改。生产防火墙验证必须取得明确授权后执行。

## 对照实验

| 观察位置与方式 | 结果 | 说明 |
|---|---:|---|
| 外部Windows，两个证书覆盖域名，TLS1.2/1.3与ALPN组合 | 6/16成功 | 未发现稳定对应某个协议/域名的失败模式 |
| 服务器到回环443，同样矩阵 | 16/16成功 | Nginx本地处理正常 |
| 服务器到自身公网地址443，同样矩阵 | 16/16成功 | 服务器侧访问也正常，不代表外部路径正常 |
| 同一Windows TLS库，经现有SSH的临时进程内通道到同一Nginx443 | 6/6成功 | 证书校验保持开启，支持把重点收敛到公网443路径 |
| 外部直连，再次小样本 | 3/6成功 | 间歇现象仍在 |
| 已配置的本机7890代理 | 0/6成功 | 本机有mihomo进程及系统代理，但不能仅据此认定其为根因 |

临时SSH通道只用于对照，未新增监听端口、未部署长期隧道，验证后关闭。检查均为少量静态首页请求，未发送业务凭据或采集用户位置。

## 包头证据

短时观察服务器TCP包头，不输出请求正文、TLS密钥或代理凭据。同一TCP连接中出现：

- 正常SYN、ACK、ClientHello等入站包TTL为114，IP标识连续。
- 中途到达的RST包TTL为248，IP标识与上述序列不连续。
- 部分RST到达后客户端仍有原连接的后续数据，服务器随后才因连接已消失发送RST。

该差异支持“链路中有异常重置包”的判断，不能仅凭TTL定位具体设备、服务商或策略。不能把服务器后续发出的RST误当成最初断开的唯一原因。

Nginx443监听、证书校验、服务器本地请求正常；检查未发现本机443拒绝规则或容器443转发。DNS A记录指向现有服务器，AAAA查询未返回地址。

## 下一项验证的设计

为验证异常RST与失败是否存在因果关系，准备一个窄范围A/B实验：

1. 先记录未过滤时的8次请求结果。
2. 备份当前iptables规则，先安排120秒自动删除任务，再加临时规则。
3. 规则只匹配入站TCP目的端口443、RST标志、TTL恰好248，不改变普通数据包、SSH或其他端口。
4. 再做16次同样请求，并读取该规则匹配计数。
5. 正常结束立即删除规则；异常中断由预设任务删除。

这是诊断实验，不是已经验证的永久修复。匹配条件也可能命中某些合法RST，必须确认风险并明确授权后执行，不能因为有回滚就跳过授权。

自动审批已拒绝未经明确授权的生产防火墙变更；当时只准备了脚本，未执行规则安装。后续执行结果应追加记录，不覆盖上述历史事实。
