# 审核模块重构

## 边界

保持 `/pet-system/admin/audit/**` 路径及原 DTO。新代码位于 `refactor/audit`，旧 Controller、实体、Mapper、服务、审核写策略均保留，未修改表结构。

`PmsAuditServiceImpl` 将查询交给 `AuditQueryService`，将提交、单条和批量决策交给
`AuditCommandService`。详情复用原 `AuditTargetHandlerFactory` 的只读转换，不再调用旧
`AuditServiceImpl`；旧实现留在仓库供回退。

## 查询结构

`AuditQuerySource` 负责各内容类型的查询和投影；`AuditQuerySources` 注册领养、救助、活动、日常四个适配器。`StrategyRegistry` 负责类型索引和重复键检查。查询服务统一完成日期范围、排序、分页与作者批量装配。

历史查询按内容类型收集目标 ID，再批量加载目标元数据；当前页的作者和审核人合并查询，避免逐条加载。日常动态的待审标题仍用 50 字预览，历史标题保持完整正文，避免关键词落在预览之外时漏查。

## 有意修正

- 待审列表页码超出范围：返回空 records 和正确 total，避免 subList 越界。
- 历史关键词先过滤后分页：total 对应真正匹配的目标，避免空页与错误总数。
- 目标内容为 null：截断函数不再抛 NPE。
- 同时间内容增加类型和 ID 排序，保证分页稳定。
- 无效类型显式报参数错误，不再静默返回空列表；分页采用共享上限 100。
- 历史中已不存在的目标不计入可展示总数；未知历史类型在不指定类型查询时跳过。

## 尚存限制

跨内容类型的待审查询仍先汇总后分页，与旧实现相同。历史查询为保证关键词过滤与总数一致，当前也会加载符合基础条件的全部记录；这不是适合大规模数据的最终方案。后续应在切表阶段引入统一审核读模型或数据库 UNION 查询，在 SQL 层过滤与分页。

本轮不部署服务器，不修改历史审核数据。

## 写链路（第二批）

- `AuditWriteTarget` 注册四种审核类型，负责目标锁定、快照读取和数据库状态更新。
- `AuditWriteMapper` 使用固定表名 SQL：先锁内容行，再对待审记录执行 FOR UPDATE 当前读。
  目标锁让新提交串行化；当前读避免加入已有事务时被可重复读快照误导。
- 审核记录 UPDATE 带 `audit_status=0` 条件，检查受影响行数；内容 UPDATE 同样要求待审状态。
  任一步失败即回滚，同一事务内不会留下只有记录改变或只有内容改变的半完成结果。
- 批量审核仍是整批成功或回滚；上限 100，去重后按 ID 升序获取锁，降低反向锁序死锁风险。
- 历史重复待审记录不自动清理，显式报错，避免任意选择一条。
- `AuditChangedListener` 在提交后清缓存、发通知、发布现有搜索同步事件。
  保留原通知参数，日常动态仍不发审核站内通知；内容的通过/拒绝状态映射保持原样。
- 外部副作用单独捕获并记录失败，某项失败不阻断其它项，也不伪装成数据库回滚。

## 验证边界

单元测试覆盖重复提交、重复/失效审核记录、条件更新失败、拒绝原因、权限和批次锁序。
Spring 事务同步测试覆盖提交后投递，以及后续批次失败时抑制先前事件；它使用 Mock 数据访问，
不等价于实际 MySQL 的锁竞争测试，也不证明数据库回滚本身。

当前事件没有持久化重放，提交后进程退出可能丢失副作用；异步搜索监听器自己的失败也不在
当前监听器的同步异常捕获范围内。后续需要完成 Outbox 重放与幂等消费后再承诺可靠投递。

锁协议覆盖经由新 `AuditCommandService` 的入口；旧后台两个HTTP审核路径已在后续步骤接入（见下文），
仍不能将此保证扩大到系统内任意直接改表的调用。现有缓存驱逐仍复用旧处理器的区域口径，
没有在本轮扩大为全区域失效。

## MySQL 并发集成测试（待执行）

`AuditMySqlConcurrencyTest` 使用真实 Spring DataSourceTransactionManager、SqlSessionTemplate
和 InnoDB。仅在 `PMS_AUDIT_MYSQL_TESTS=true` 且提供测试库密码时运行。

地址门禁拒绝服务器地址和业务库名，仅允许 `localhost` / `127.0.0.1:3306/pet_system_test`，
连接后再确认 SELECT DATABASE() 及关键表 InnoDB 引擎。表结构需事先存在，测试不创建/修改表。

测试只自动生成随机标题标记的帖子，并记录生成的 ID。清理审核记录时会 JOIN 回帖子、核对 ID
和随机标记；不会使用清空整表的种子脚本，不删除预存业务行。测试被强制终止可能留下带标记的
测试行，需人工核实后清理。

覆盖四项：并发提交只保留一个申请；并发审批只有一次提交；批次后续目标写入失败时前面所有
数据库修改和事件回滚；另一事务持有目标行锁时新提交等待、锁释放后继续。

2026-10-23 后续验证：用户明确授权本机测试库后，最初四个场景真实执行通过，均未跳过。
继续接入旧后台审核入口后，增加了“旧入口与新入口同时审批同一帖子”的竞争场景；五项
MySQL 集成测试全部通过。测试使用本机 pet_system_test，无表结构修改，无全表种子重置。

## 旧后台审核入口收口

`refactor/admin/PmsAdminServiceImpl` 实现原 `AdminService` 并标记 `@Primary`，原 Controller
不变，因此以下路径仍可用：

- POST /pet-system/admin/pet_post/accept
- POST /pet-system/admin/pet_post/reject

这两个方法根据帖子类型路由到统一 `AuditCommandService`。初始查询只决定 adopt/help 路由，
实际类型、内容状态和待审记录仍在命令服务持有目标行锁时核对；并发修改类型不会绕过核对。

有意改变：原入口通过只设 status=1、拒绝写 status=5，均不维护审核记录与 audit_status。
现在统一维护两者，拒绝使用既有标准审核流程的 audit_status=2/status=0 映射，不再写无定义的5。
没有待审记录时明确拒绝，不自动补造记录或重复发通知。

账号查询、批量禁用、启用、重置密码明确委托名为 adminServiceImpl 的旧 Bean，事务代理仍保留。
这不是账号管理模块整体重写。新增7个单元/装配测试覆盖路由、权限、账号功能委托和删新后回退。
未修改任何旧 Controller/Service 或 DTO，也未部署服务器。

上述两个旧后台HTTP审核路径与标准审核路径现在遵守相同锁协议。其他模块直接改表或发布者
编辑内容的并发协调不在本轮保证范围，仍需在对应模块迁移时逐一核对。
