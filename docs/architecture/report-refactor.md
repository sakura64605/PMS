# 举报模块重构

## 接管方式与兼容范围

新代码位于 `com.hongjie.pms.refactor.report`。`PmsReportServiceImpl` 实现原 `ReportService`，通过 `@Primary` 接管原 Controller 的注入；旧 Controller、Service 实现、DTO 和表均保留。本次没有 DDL、前端修改或部署。

保留 `/pet-system/report` 下的 submit、list、handle/{id}、detail/{id} 路径和原响应 DTO。目标类型读取兼容历史别名，写入仍使用 report_record 的 pet/activity/comment/user 方言。暂不增加日常动态举报支持。

请求校验有所收紧：目标 ID 必须为正数，举报原因及处理结果必须为 1—200 个字符；处理状态只能为 1（已处理）或 2（已驳回）。提交者和处理者必须匹配当前登录上下文，管理查询及处理要求管理员权限。提交时要求目标存在。

## 设计与事务

- 策略注册表：`ReportTarget` 隔离宠物、活动、评论、用户的锁定、批量标题读取和处置行为，复用已有类型编码器及 `StrategyRegistry`。
- 应用服务：统一状态校验、事务和 DTO 批量装配，列表按目标类型批量查询，避免逐条加载关联数据。
- 并发写：提交先锁目标，再以当前读检查同一用户对同一目标的待处理举报（含别名）；处理以 `id + status=0` 条件更新争抢处理权。提交和受理保持目标先于举报记录的锁顺序。此协议作用于新服务入口，不约束其他直接写表代码。
- 本地事务：举报状态、目标处置、用户禁言/禁用和恢复任务的数据库写入共用事务。任务写入继续复用现有 DelayTaskService，不另建调度机制。
- 提交后事件：宠物/活动缓存失效及搜索同步事件由 `@TransactionalEventListener` 在提交后触发。单项失败记录日志并继续其他项；没有持久化 outbox 或自动补偿保证。

## 修复及业务边界

活动举报受理后，将报名中或进行中的活动设为合法的下架状态 3（旧逻辑写入未定义的 4）；已结束活动不改状态。宠物仅从已发布状态下架。

评论从正常状态删除时，实际落库作者禁言标记和截止时间，并写入恢复任务；不缩短已有更长的禁言。已删除评论再次被受理不会重复处罚。用户仅从正常状态禁用时创建恢复任务。原有一天处罚时长和不发送举报通知的行为保留。

已不存在的目标仍可完成历史举报处理，但不再执行目标处置。未知历史目标可以驳回；受理未知类型会报参数错误。列表对未知类型和已删除目标保留兜底展示。

仍沿用旧评论删除计数规则、旧账号鉴权和恢复任务处理逻辑：本次不增加评论计数回减、不处理已签发 JWT 的主动撤销；旧封禁恢复任务可能覆盖期间发生的人工禁用，后续需要处罚模型区分来源和有效期。

## 验证与回退

新增 19 个测试：提交去重与身份校验、条件状态更新、策略处置、批量查询、Spring 主服务接管、真实事务同步的提交/回滚以及缓存失败隔离。Spring 事务测试使用内存事务管理器及 Mapper mock，不代替 MySQL 行锁、SQL 执行或数据库回滚集成验证。

整体回归关闭数据库测试，避免触发测试库的全表种子重置。2026-10-23 验证：排除依赖外部基础设施的 PmsApplicationTests 后，188 项中 183 项通过、5 项 MySQL 集成测试跳过，无失败。直接运行完整测试时，原 contextLoads 因知识库初始化无法获取 MySQL 连接失败；未声称完整应用启动验证通过。后续已在本机 pet_system_test 单独运行 ReportMySqlConcurrencyTest：7 项全部通过（历史别名并发提交去重、并发受理、受理与驳回竞争、同用户多举报只创建一份封禁恢复任务、评论禁言与恢复任务只写入一次、外层事务回滚、实际目标行锁阻塞）。SQL、行锁及恢复任务写入使用真实 MySQL，缓存与外部搜索服务不在该集成测试范围内。每轮只清理随机标记的测试记录，没有运行全表种子或改表。

回退时排除 `refactor.report` 的组件及 Mapper 扫描，原 ReportServiceImpl 即可重新接管；因本次未改表，不需要反向迁移。仅移除 @Primary 会产生双实现注入歧义，不能作为回退方法。
