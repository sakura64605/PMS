# 关注模块重构

## 范围与接管

新实现位于 `refactor.following`，通过 `@Primary` 实现原 `FollowService` 并接管原 `FollowingController`。旧实现、实体和 DTO 全部保留，沿用 follow、user、user_inbox 表，没有 DDL 或前端修改。

`POST /pet-system/follow` 保持原“切换关注状态”的语义和返回结构。它不是幂等的设置操作；两个成功请求串行后会依次关注、取消关注。不把并发点击解释为同一次请求，若未来需要幂等设置，应增加带期望状态的接口。

`GET /pet-system/following/list` 与 `/follower/list` 保留原路径及 DTO，修复分页 total 丢失，并根据当前查看者的真实关注关系计算 isFollow；粉丝并不必然是已回关用户。分页采用公共 PageQuery 的边界及上限，排序为创建时间和 ID 降序。

## 数据一致性与分层

`PmsFollowServiceImpl` 负责身份校验、事务与列表装配；`FollowWriteMapper` 负责当前读、关系写入和原子计数；`FollowInboxWriter` 单独负责关系对应的历史动态投影；`FollowCreated` 事件通过监听器触发提交后通知。没有为每种目标额外增加策略类，因为关注关系只有一种业务类型。

写入前校验当前登录者、正数 ID 和禁止关注自己，按用户 ID 从小到大锁定双方用户行，然后用正确的 follower_id -> following_id 方向查询关系。修复旧代码的方向反转，避免误删对方对自己的关注。不存在的用户不能关注，禁用用户不能建立新关系，但仍允许取消已有关系。

关系增删、双方计数和收件箱历史回填/清理处于同一数据库事务，任意失败整体回滚。计数使用原子增减并限制不低于零，不尝试自动修复既有历史计数偏差。用户行锁使同一对用户以及共享用户的关注写入串行，优先保证一致性；高关注并发下可能成为热点。此协议不约束绕过新服务的直接 SQL 或旧写入口。

历史回填分别批量获取最多 20 条宠物帖子和 20 条活动，合并排序后保留最新 20 条；直接使用已读取对象的标题和图片，不按帖子 ID 再跨表查询。宠物类型写 pet、活动写 activity，以匹配现有 Feed 消费逻辑；修复原回填写 adopt/help 后被 Feed 忽略，以及宠物标题/封面误查活动表的问题。仅清理当前关注者和作者对应的收件箱；动态发布并发扇出仍沿用旧 Feed 机制，未新增全链路投影唯一键或重放协议。活动回填仍保持原筛选的 status=1，不扩大可见内容范围。

通知只在关注提交后发送，链接指向关注者主页。由于 MQ 失败时旧消息模块会降级本地落库，监听器使用独立新事务承载通知，避免借用已提交事务后写入未能提交。通知失败记录日志，不影响已提交关系；没有持久化 outbox、自动补偿或投递恰好一次保证。

## 验证与回退

单元测试覆盖关系方向、固定锁顺序、身份/状态校验、取消关注、失败不发布事件、分页与回关标记，以及历史内容来源和条数上限。真实数据库测试显式启用 PMS_FOLLOW_MYSQL_TESTS，限制本机 3306 的 pet_system_test，使用随机标记用户与记录，并仅清理自身数据，不灌全表种子。

数据库场景覆盖并发双次切换、双向关系并存及单向取消、真实事务回滚（含计数和历史收件箱）、旧 Controller 的主实现接管、通知失败隔离、通知降级数据库写独立提交及实际用户行锁阻塞。外部 MQ/WebSocket 采用 mock，未验证外部服务投递。

2026-10-23 验证结果：关注 12 项单元测试和 7 项 MySQL 测试全部通过；与举报 7 项 MySQL 测试一起运行共 26 项全部通过。关闭数据库测试、排除原有依赖外部服务的 PmsApplicationTests 后，整体回归 214 项中 195 项通过、19 项显式跳过，无失败。数据库并发测试已按前述独立命令执行，不依赖整体回归中的跳过结果。完整应用启动和外部中间件联调未在本轮验证。

回退需要排除整个 refactor.following 组件及 Mapper 扫描，令旧 FollowServiceImpl 重新接管；不能仅去掉 @Primary 导致双实现注入歧义。本次没有反向表迁移需求。尚未提交或部署。
