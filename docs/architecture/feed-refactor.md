# Feed 动态流重构

## 接管与模型兼容

`refactor.feed.PmsFeedServiceImpl` 实现旧 FeedService，通过 @Primary 接管原 FeedController 和发布服务的接口注入。旧实现、DTO、实体均保留；GET /pet-system/feed/home 和 /unread-count 的路径、请求参数、响应字段不变。本轮没有表结构迁移、前端修改、自动提交或部署。

沿用 follow、user_inbox、big_v_config、pet_post、activity、user 表。动态身份为 `(post_type, post_id)`，避免不同表相同 ID 被混为一条。响应及新投影的类型统一为现有前端识别的 pet/activity；历史投影兼容 pet/pet_post/adopt/help、activity/pet_activity/pet_event，忽略大小写。

## 读模型和分页

FeedSql 是分页、总数、未读数共用的可见性规则：必须仍关注作者，内容审核通过且 status=1，活动还要求 deleted=0；活动可见状态保持旧 Feed 的 1，没有扩大到报名中或已结束。普通作者要求存在相应收件箱投影，拉模式作者可直接读取可见内容。两类来源在 SQL 中 UNION ALL 后统一排序、分页，不再分别取页后拼接。

使用 EXISTS 判断关系、投影和拉模式，避免重复历史投影放大列表/计数。同一创建时间按类型和 ID 稳定排序。分页返回可见内容的真实 total，默认每页 20、最大 100；保留 offset 分页，未引入游标。跨请求期间有新内容或模式变化时，offset 分页仍可能移动，不能声称跨请求快照或严格无重复。

FeedAssembler 按类型批量读完整内容、一次批量读作者，保留 SQL 页顺序，使用当前内容、封面及作者资料；不依赖历史冗余资料。原 DTO 的 isLiked/isFavorite 仍保持未填充，不借此新增互动查询。

首页读取处于 REPEATABLE_READ 事务中，令 total、页身份和批量装配共享数据库快照。只对本页实际返回的身份更新当前用户的未读投影，包含同一内容的历史别名投影；其他用户与其他页不受影响。更新失败会使整个读取事务失败并回滚，不再静默降级逐条更新。

未读数按可见动态身份去重，排除已取消关注、未审核、下架、删除和不支持类型的投影。拉模式内容若没有投影，不凭空创建未读状态；尚未引入拉模式读游标或逐内容阅读表。原 int 接口对极大计数饱和到 Integer.MAX_VALUE。

## 写模型和复用

推送前锁作者用户行，按实际关注关系数量维护 big_v_config；超过 1000 粉丝沿用拉模式，不扇出。普通作者通过一条 INSERT SELECT 向现有粉丝写投影，并在写入中排除同一接收者、作者、内容身份的已有历史别名投影。新入口的同作者并发推送因作者锁串行，重复调用不会重复插入；没有新增数据库唯一键，不约束旧代码或直接 SQL 绕过锁的写入。

投影写入和模式更新共用调用方数据库事务，可一起回滚。推送输入的目标类型经现有 TargetTypeCodec 规范化，仅允许宠物和活动。服务写方法是原有内部调用契约，不新增公开写接口；实际阅读始终回到内容表验证可见性。

关注模块的 FollowInboxWriter 继续承载历史回填。原 populate(follower,author) 默认 20 条不变，新增有界 limit 重载，供旧 FeedService.pullHistoryPosts 入口复用，避免再复制一次回填装配。Feed 的历史回填和清理入口按用户 ID 升序锁定双方，与关注写入保持同一顺序。Feed 推送锁作者行，与这些路径协调；其他旧写路径不在此保证范围。

模式阈值在发布/推送时更新，不是实时统计系统。从拉模式转为推模式时，既有未投影内容不会自动全量回填；从推模式转拉模式时，直接读取范围可能扩大。重构保留这一模型边界，后续若要求切换无损，需要单独的回填任务及进度模型。

## 验证与运维边界

Feed 单元测试覆盖实际返回内容才标已读、空页 total、页大小上限、匿名拦截、类型规范化、推拉阈值分支、旧回填入口复用、跨类型相同 ID 装配与批量作者查询。

FeedMySqlTest 显式开启 PMS_FEED_MYSQL_TESTS，强制本机 3306 的 pet_system_test 和 InnoDB；只创建随机标记的用户、内容、关系、投影及模式配置，测试后按所属用户及标记清理并确认用户已移除，无全表种子、无改表。场景包括混合来源排序分页、历史别名去重、可见性与未读过滤、分页已读隔离、纯拉模式多页、并发重复推送、模式/投影事务回滚、已读事务回滚及 Controller 接管/回填 limit。

2026-10-23 验证结果：Feed 9 项单元测试及 9 项真实 MySQL 测试全部通过；与关注模块复验合计 37 项全部通过，其中数据库场景 16 项。关闭数据库测试并排除原有 PmsApplicationTests 后，整体回归 232 项中 204 项通过、28 项显式跳过，无失败。数据库用例已按前述独立运行，不将跳过视为验证成功。

这是正确性验证，未进行大规模压测或生产 EXPLAIN。当前 correlated EXISTS 依赖既有索引，大量历史投影和深 offset 页可能昂贵；若实际负载需要，后续应评估 user_inbox 的内容身份复合索引和游标分页。外部 MQ、搜索及完整应用启动未由这些局部测试覆盖。

回退需整体排除 refactor.feed 的组件与 Mapper 扫描，恢复旧 FeedServiceImpl 的接口注入，不能只移除 @Primary 造成双实现歧义。复用的 FollowInboxWriter limit 重载对原调用无破坏，可以保留；无需反向表迁移。
