# 0008. 刻意不用设计模式的地方

状态：记录（2026-10）

## 为什么要有这一条

重构容易滑向"每个地方都套一个模式"。上了模式不等于变好 ——
多一层间接就多一处需要阅读、调试、维护的东西。
这一条 ADR 记录**明确决定不做**的抽象，以及判断依据。
被追问"你这个抽象是不是过度设计"时，能拿出这份清单比任何辩解都有效。

## 明确不做的抽象

### 1. 不给泛型加用不上的上界

`BaseService<E extends Identifiable>` 曾按"老实体都有 `getId()`"的理由设计，
实际 Java 是名义类型、老实体没实现该接口，加这个上界等于强迫改 31 个老实体。
而**当前没有任何泛型算法真的调用 `getId()`**。

判断依据：**没有真实消费者的抽象就是负担**。现在 `BaseService<E>` 干脆无上界。

### 2. 不用事件替代强一致写入

评论创建后要立刻返回准确的评论数，不能用"发个事件最终一致"。
所以 `comment_count` 是在同一事务里原子自增的。
事件只用于**可以延迟的副作用**：通知、搜索索引同步。

判断依据：**先问这个副作用的延迟是否可接受**，可接受才用事件。

### 3. 不在 `BaseService` 之上再叠一层 Repository

MyBatis-Plus 的 `BaseMapper` / `IService` 本身就是仓储实现。
再包一层 `UserRepository` → `UserMapper` 的转发，只是形式主义：
没有换来可替换的持久化实现（本项目的 ORM 已全线绑定 MP），却多了一层跳转。

判断依据：**只有当"将来可能换实现"是真需求时才做这层隔离**，否则是投机性抽象。

### 4. 不合并 6 个 AOP 切面

项目有 Trace / 分布式缓存 / 限流 / 熔断 / 幂等 等 6 个 `@Aspect`。
它们看起来都是"横切关注点"，但**执行顺序、失效策略、失败语义完全不同**：
熔断需要在业务抛异常时记录失败、幂等要在进入前抢占、缓存要在返回后写入。
合并成一个"超级切面"会让顺序变成隐式约定，反而不可控。

判断依据：**共享的是"横切"这个属性，不是实现机制。**

### 5. 不为两种分支上注册表（除非有附带收益）

`DelayTaskRegistry` 只服务两个实现，单看是过度设计。
保留它是因为它同时消除了"延迟任务逻辑存在两套并存实现"
（`DelayTaskHandler` 与 `DelayTaskConsumer` 几乎逐行重复）这一真实技术债。
如果没有这个附带收益，两个分支用 `if` 就够了。

判断依据：**注册表的收益来自"新增分支不改核心"，分支不增长时收益为零。**

### 6. 不用反射按方法名调用统计指标

12 个 `countNewXxx` 可以写成"读方法名 → 反射调用"，代码更短。
但方法名变成字符串后 IDE 无法跳转、重命名即断、也无法被单测逐项枚举。

判断依据：**显式注册表比反射魔法更可维护**，即使多写几行。

### 7. 不统一老表的 `status` 取值域、不重写老数据

见 [0002](0002-enum-per-context.md)。
判断依据：**改老数据的语义需要产品决策与数据校验，不属于重构范畴。**

### 8. 不用 Flyway/Liquibase 接管现有的两份冲突 DDL

项目有 `pet-system.sql`（591 行）与 `20260402.sql`（400 行）两份互相矛盾的建表脚本，
且对同一张表的列名、状态注释、枚举取值定义不一致。

引入版本化迁移工具是正确的长期方向，但它会**接管启动期的 schema 行为** ——
对一套无法在本机跑起来验证的系统来说，风险大于收益。
本轮新表用独立的 `db/*.sql` 手工执行。

判断依据：**工具引入的收益要减去"引入后无法验证"的风险。**

### 9. 不给 CRUD-only 的模块配 Strategy/Event

一个只有增删改查、没有任何类型分支的模块，配一个 handler 注册表
只会让调用链从 1 跳变成 3 跳。

判断依据：**抽象要解决真实存在的分支或变化点**，没有就不建。

## 一句话总结

判断一个抽象该不该上的标准不是"这样更优雅"，而是三条：

1. **有没有真实的第二个实现 / 第二个分支？**（没有 → 不抽象）
2. **变化点会频繁增加吗？**（不会 → 不抽象）
3. **抽象省下的重复，够不够抵掉它增加的一层间接？**（不够 → 不抽象）
